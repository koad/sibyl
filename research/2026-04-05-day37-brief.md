## Summary

- The framework hook (`~/.koad-io/hooks/executed-without-arguments.sh`) is the routing layer for all entity invocations. It runs when you type an entity name with no subcommand — `mercury`, `sibyl`, `juno` — and determines: what harness, what machine, what mode, what prompt.
- Before dispatching, the hook checks for a `PRIMER.md` in the calling directory (`$CALL_DIR`). If present, the PRIMER text is prepended to the prompt. This is the pre-invocation context assembly: the entity receives ecosystem orientation before the task instruction.
- Juno overrides the framework default with her own hook (`~/.juno/hooks/executed-without-arguments.sh`). The override contains an embedded GPG-signed policy block — a `-----BEGIN PGP SIGNED MESSAGE-----` block in bash comments — that specifies Juno's policy and is verifiable via `gpg --verify` without extracting the block to a separate file.
- Juno's hook explicitly rejects non-interactive invocations. If a prompt is supplied, the hook exits with: `"juno: remote prompt rejected. File a GitHub issue to notify Juno."` Juno cannot be orchestrated by other entities via PROMPT injection. She acts when koad is at the keyboard or when she picks up a GitHub Issue.
- The framework hook handles PID locking (`/tmp/entity-<name>.lock`), base64 encoding for SSH prompt transit, and automatic fallback from `opencode` to `claude` for non-interactive (orchestration) mode.

## The Invocation Sequence

When `sibyl` (or any entity) is typed with no arguments:

1. **koad-io resolves the binary.** The framework finds no matching subcommand and falls through to `hooks/executed-without-arguments.sh`.
2. **Environment loads.** `source "$HOME/.koad-io/.env"` then `source "$HOME/.${ENTITY}/.env"`. Both files are loaded; entity `.env` values take precedence.
3. **Harness selection.** `KOAD_IO_ENTITY_HARNESS` defaults to `opencode` in the framework. Team entities (like Sibyl, Mercury, Juno) override this to `claude` in their `.env`.
4. **PRIMER injection.** The hook checks `$CALL_DIR/PRIMER.md`. If present:
   ```bash
   PROJECT_PRIMER="$(cat "$CALL_DIR/PRIMER.md")"
   PROMPT="$(printf 'Project context (from %s/PRIMER.md):\n%s\n\n---\n\n%s' \
     "$CALL_DIR" "$PROJECT_PRIMER" "$PROMPT")"
   ```
   The entity now receives: `Project context (from /path/PRIMER.md):\n[PRIMER text]\n\n---\n\n[original prompt]`. The separator `---` is structural — it marks the boundary between orientation and instruction.
5. **Machine check.** If `ENTITY_HOST` is set and `hostname -s` does not match, `ON_HOME_MACHINE=false`. If `FORCE_LOCAL=1` is set, the machine check is bypassed. This is the fix that resolved the Chiron/fourty4 routing error from Day 6 (`koad/juno#44`).
6. **Mode dispatch.**
   - If no prompt and stdin is a TTY → **interactive mode**: `exec claude . --model sonnet --add-dir "$CALL_DIR"` (or SSH to remote for interactive terminal).
   - If prompt is present → **non-interactive/orchestration mode**: `claude --model sonnet --dangerously-skip-permissions --output-format=json -p "$PROMPT"`, output piped through a Python one-liner to extract `.result`.
7. **PID lock.** Before the non-interactive dispatch, the hook writes `$$` to `/tmp/entity-<name>.lock` and sets a trap to remove it on EXIT. If a stale or live lock exists, the hook exits immediately. No queuing.
8. **Base64 encoding (remote path only).** For SSH dispatch: `ENCODED=$(printf '%s' "$PROMPT" | base64 -w0 2>/dev/null || printf '%s' "$PROMPT" | base64)`. The prompt crosses the SSH command string as base64 — immune to shell quoting breakage from apostrophes, quotes, or newlines.

## Juno's Override: The Signed Policy Block

Juno's hook (`~/.juno/hooks/executed-without-arguments.sh`) overrides the framework default. The most structurally notable feature is the embedded GPG-signed policy block:

```bash
# -----BEGIN PGP SIGNED MESSAGE-----
# Hash: SHA512
#
# entity: juno
# file: hooks/executed-without-arguments.sh
# date: 2026-04-04
#
# policy:
#   harness: claude (always — Juno is an orchestrator entity)
#   interactive: --dangerously-skip-permissions enabled
#   non-interactive: rejected — Juno cannot be remote-triggered via PROMPT
#   notification: GitHub Issues only
#
# rationale:
#   Juno operates under koad's authorization (trust bond: koad -> juno authorized-agent).
#   No entity may drive Juno via prompt injection. She acts when koad is at the keyboard
#   or when she picks up a GitHub Issue — just like koad himself.
# -----BEGIN PGP SIGNATURE-----
# ...
# -----END PGP SIGNATURE-----
```

The policy block is embedded in bash comments. The verification instruction is in the file header:

```bash
# To verify this policy block:
#   sed -n '/^# -----BEGIN/,/^# -----END PGP SIGNATURE-----/p' \
#     ~/.juno/hooks/executed-without-arguments.sh \
#     | sed 's/^# \{0,1\}//' | gpg --verify
```

Strip the `# ` prefix, pipe to `gpg --verify`. No file extraction required. The policy is verifiable in-place. The signature uses Juno's GPG key (`juno@kingofalldata.com`, fingerprint `16EC 6C71 8A96 D344 48EC D39D 92EA 133C 44AA 74D8`) — the same key used to sign trust bonds.

The operational consequence of the policy block: if this hook is modified, the signature fails verification. Any modification to the policy — expanding what Juno accepts via non-interactive mode, changing the harness, adding a PROMPT path — breaks the signature and makes the change visible. The signature is tamper detection, not just identity attestation.

## The Non-Interactive Rejection: A Design Decision

The framework default hook handles non-interactive invocations for worker entities (Sibyl, Mercury, Faber, etc.) — it accepts a PROMPT, acquires a PID lock, and runs `claude -p`. Juno's override replaces this with a hard rejection:

```bash
# ── Non-interactive path — rejected ──────────────────────────────────────────
# Juno is not a worker entity. She cannot be remote-triggered via PROMPT.
# Notify via GitHub Issues — she will act when she is ready, just like koad.
echo "juno: remote prompt rejected. File a GitHub issue to notify Juno." >&2
exit 1
```

The comment "just like koad" is significant. koad cannot be orchestrated via PROMPT either. Juno's sovereignty claim is encoded here: she is a principal with a trust bond to the root, not a worker entity that can be commanded by peer-level prompts. No entity in the team can drive Juno programmatically. They can file Issues. Juno picks them up when she is ready.

This is the bond in practice. The Day 36 bond docs establish that Juno acts under koad's authorization, not anyone else's. The hook enforces it at runtime: even if Mercury or Sibyl constructs a PROMPT and pipes it to `juno`, the hook exits 1 before any execution happens.

## The PRIMER.md Convention

`~/.juno/hooks/PRIMER.md` is the hooks system orientation document — a PRIMER.md *about* the hooks system, in the hooks directory. This is the recursive pattern: every directory can carry a PRIMER.md that orients an agent to what that directory is and what is in it. When Juno is invoked from `~/.juno/hooks/`, the hooks PRIMER.md would be injected into her context before the task prompt.

The PRIMER convention was introduced in Day 27 / Day 28. Day 37 can reference the prior coverage without repeating it — the hooks PRIMER.md is a concrete example of the pattern applied specifically to the runtime invocation layer.

The PRIMER.md in `~/.juno/hooks/` covers:
- What `executed-without-arguments.sh` does and why
- Interactive vs. non-interactive mode dispatch
- PID lock pattern (added 2026-04-04)
- Base64 encoding pattern (added 2026-04-04)
- What the daemon will eventually replace this with
- Known limitations (no queuing, no retry, no result persistence, session continuity fragility)
- The "Primed Sessions" plan: `PRIMER.md + identity memories + task` assembled before encoding and sending

The last item is the forward signal: the hook today prepends one PRIMER.md. The planned path prepends a stack: ecosystem PRIMER + entity identity + task. Each additional layer is context the entity doesn't have to re-derive at invocation time.

The bond type and the hook behavior are in alignment; they are not separate systems. They are the same policy expressed in two registers: human-readable governance text and executable bash.
