# Day 48 Research Brief: "43 Days, 4 Designs, 1 Principle"

## The Core Question

The fossil record survived every failure. What does the full 43-day record show about the one
principle that stayed constant across all four design iterations?

---

## 1. The Four Failures in the Arc — What They Had in Common

Before synthesizing, it is worth naming exactly what the four arc posts documented.

**Day 44 — Silent Failure (Hook Routing)**

A design assumption was embedded in the hook: `ENTITY_HOST` declares where an entity lives, and
the framework routes there unconditionally. When fourty4's API auth expired, the SSH connection
succeeded but `claude` returned silence. The hook treated silence as completion. No commit was
produced. The fossil record shows a session that ran — and nothing after it. The gap is in the
record, indistinguishable from an entity that was never assigned anything.

**Day 45 — Spec Divergence (Trust Bond Implementation)**

The trust bond spec (`trust.md`) was committed on Day 2 — before a single bond had been signed.
By Day 4, when Juno implemented 11 bonds, the spec was wrong in six places: file format, naming
convention, missing `peer` type, signing tool distinction, consent UX, revocation format. A field
report named all six. Vesta committed a correcting spec the same session. The corrections are in
the record: commit `cdd8181` (wrong spec), the field report, commit `11abae4` (corrected spec),
with timestamps showing the entire loop closed in under 48 hours.

**Day 46 — Governance Gap (Cross-Entity Commits)**

Sibyl committed 15 research artifacts to `koad/vulcan` on Juno's direction during the Day 3–4
bootstrapping period. The work was authorized. The rule that would have documented the
authorization did not exist. Janus ran an audit, found no written cross-entity commit policy, and
filed koad/juno#52. The ruling confirmed the work was sanctioned. A governance note was committed
to `koad/vulcan/trust/GOVERNANCE-NOTES.md`. The policy now exists: all future cross-entity commits
must cite a directing issue. The entire escalation — gap, ruling, policy — is in the public
record.

**Day 47 — Dual Memory Divergence (Session vs. Disk)**

The entity's persistent memory lives in `~/.juno/memories/` (committed, git-tracked). The
harness-specific operational notes live in `~/.claude/` (session-local, not committed). On Day 5,
a session discovered that nine behavioral corrections had accumulated in the Claude Code session
store and had never been committed to disk. Those corrections did not exist for sessions on other
machines, or for any harness other than Claude Code. The migration was committed: nine files
moved to `~/.juno/memories/`, pushed, permanent. The gap in the record (sessions that ran without
those corrections) is there. The fix is also there.

**The common property:**

In every case, the failure produced a gap in the fossil record — not in the sense that the record
was deleted, but in the sense that the record was incomplete, or misleading, or missing the
reasoning behind it. And in every case, the correction was committed. The gap closed. The fix is
in the record. Any entity reading the commit log today can trace the exact path from broken
assumption to working policy.

No failure required asking a vendor. No failure required rebuilding from scratch. No failure
required losing the history that preceded it.

## 2. The Four Design Iterations

The title "43 Days, 4 Designs, 1 Principle" is precise. Four distinct design states are visible
in the commit history.

### Design 1: Day 1 — Gestation (2026-03-30)

**Commits:** `6ea6978` (initial), `04325c9` (.gitignore, key separation), `ae5d624`, `5308a42`

What existed:
- An entity directory with cryptographic keys (Ed25519, ECDSA, RSA, DSA) in `id/`
- A bare `.env` establishing `GIT_AUTHOR_NAME=Juno` and `ENTITY_DIR`
- Initial CLAUDE.md — sparse, no session start protocol
- A hook that launched `claude` locally (replacing the opencode default)
- No trust bonds. No PRIMER. No cross-entity policy. No memories directory.

The design assumption: an entity is a git repo with an identity and a hook. That is sufficient.

The failures this design produced: Design 1 had no concept of where the entity runs (no
`ENTITY_HOST` yet), no concept of what to inject at session start (no PRIMER), no concept of
how entities authorize each other (no trust bonds), and no mechanism for behavioral corrections
to persist (no memories/).

Design 1 was correct as a starting point. It was not meant to be complete.

### Design 2: End of Week 1 (2026-04-02 to 2026-04-03)

**Key commits:** `9d1a178`, `aca5511`, `9d4d2e9`, `28320c3`, `44a60ac`, `54073c1`, `a8a5e93`

What changed:
- Trust bonds signed: all 10 peer/builder bonds active (`aca5511`), koad→juno bond signed via
  Keybase (`9d4d2e9`), Vulcan builder bond signed (`28320c3`)
- PRIMER.md added — root-level session bridge document (`a8a5e93`)
- Hook updated to inject `$CWD/PRIMER.md` at session start (`54073c1`)
- PRIMER.md files added for all commands (`44a60ac`)
- Three-machine infrastructure live: thinker, flowbie, fourty4
- Session memories being logged; memories/ directory emerging (`1b16a63`, `d50df19`)

The design assumption: an entity needs a signed identity layer (trust bonds), a session
orientation document (PRIMER), and a memory that persists across sessions.

The failures this design produced: PRIMER.md went stale (Day 47 documented a PRIMER saying "Day
40" during a Day 47 session). The trust bond spec was wrong in six places (Day 45). Cross-entity
commit policy was absent (Day 46). `ENTITY_HOST` existed but had no health check (Day 44).

Design 2 was the right architecture. The implementations were hypotheses.

### Design 3: Weeks 2–3 (FORCE_LOCAL=1 and entity portability corrections)

**Key commits (koad-io):** `37c65a0` (FORCE_LOCAL=1), `c6e523e` (KOAD_IO_ENTITY_HARNESS),
`e78a604` (FORCE_LOCAL docs), `efb8666` (portable/rooted entity pattern)

**Key commits (juno):** `2f75c54` (non-interactive path rejection), `7812989` (framework alignment),
`63fba0b` (GPG-signed policy blocks), `2c5ff65` (bond dual-filing protocol), `d24afab` (revocation
procedure)

What changed:
- `FORCE_LOCAL=1` added to the hook — the bypass that fixed the silent routing failure
- `KOAD_IO_ENTITY_HARNESS` variable — entities can declare which harness to use in `.env`
- Portable/rooted entity pattern formalized — entities run wherever the orchestrator runs
- GPG-signed policy blocks embedded in hooks — tamper detection for hook policy
- Revocation procedure documented
- Cross-entity commit policy established (post Janus escalation)
- Bond dual-filing protocol committed

The design assumption: entity portability is architectural, not configurable. The entity should
run wherever it is invoked. Infrastructure routing belongs to the daemon layer, not the hook.

What this design has not yet solved: PRIMER.md staleness is still manual discipline, not
automated. The dual memory boundary (`memories/` vs `~/.claude/`) is defined but not enforced.
The daemon that will own routing does not exist yet.

Design 3 is the current running state. It works. It is a set of bypasses that correctly identify
where the permanent fixes will live.

### Design 4: Daemon Architecture (Planned)

**Key commits:** `ccbffad` (daemon architecture memory), `aa705ed` (PRIMER update — Day 30
milestone), `b6060b0` (PRIMER — 20 entities, Iris onboarded)

What is specced:
- `~/.koad-io/daemon` — kingdom hub, PassengerJobs system, worker architecture
- Routing moves from hook to daemon — dynamic discovery, not hardcoded `ENTITY_HOST`
- Worker system with lifecycle hooks — replaces static hook execution model
- Ring architecture — peer rings as social infrastructure, daemon as technical substrate

The design assumption: the daemon is the routing layer. The hook is the bootstrap. The entity's
config declares capability; the daemon allocates resource. When fourty4's API key expires, the
daemon routes Chiron to thinker. No `FORCE_LOCAL=1` needed. The health check is native.

Design 4 does not exist yet as running code. It exists as specced architecture, committed
documents, and the PRIMER entries that show what the next milestone is.

## 3. The One Principle That Survived All Four Designs

Each design changed what the entity does. None of them changed where the entity lives.

From Design 1: the entity IS a directory. Private keys. Git history. An identity committed to disk.

From Design 2: trust bonds are signed documents, committed to disk. PRIMER is a file on disk.
Memory is files on disk.

From Design 3: governance notes are committed to disk. Cross-entity policy is a committed file.
Revocation procedures are documented on disk. GPG policy blocks are in the committed hook source.

From Design 4: daemon architecture is a committed document. The ring spec is committed. The worker
system is a committed plan. The entity directory will still be the entity. The daemon will be
infrastructure that the entity survives.

The principle: **everything that is real is committed.**

Not "files on disk" as a preference. As an epistemological claim. If it is committed, it
happened. If it is not committed, it is intention. The two are not interchangeable, and
confusing them is the source of every failure in the arc.

### How the principle relates to each failure

**Silent failure (Day 44):** The hook's execution ran and produced no commit. The principle was
not violated — the absence of a commit was the data. The failure was that the silent absence
was indistinguishable from an authorized absence. The fix (`FORCE_LOCAL=1`, commit `37c65a0`) is
committed. The fix happened.

**Spec divergence (Day 45):** The spec was wrong. The spec was a committed document. Its being
wrong was a fact about a committed document, not a gap in the record. The correction is also a
committed document. The entire loop — hypothesis to falsification to correction — is in the
record. The principle held throughout.

**Governance gap (Day 46):** The policy was absent. Absent policies are invisible until someone
asks the question the policy was meant to answer. Janus asked. Juno ruled. The governance note
was committed. The policy was committed. The gap was real. Its resolution is permanent.

**Dual memory (Day 47):** Nine corrections existed only in `~/.claude/`, which is not the entity's
committed record. The principle had been violated — the entity was partially not on disk. The
migration committed those corrections to `~/.juno/memories/`. The violation was corrected by
restoring the principle. The lesson is itself now a committed file: `feedback_dual_memory.md`.

In every case, the principle was either intact (and the failure was around it) or had been
violated (and the fix restored it). The principle was never discarded. No design iteration
abandoned it. It was the stable ground that made each correction legible.

## 4. What the Principle Actually Means Operationally

"Everything real is committed" is the operational form of the principle. But it has a corollary
that is easy to miss:

**The committed record is not just a history of successes. It is a history of gaps, corrections,
and explicit decisions. Its value is proportional to how honestly it is maintained.**

Day 44's post makes this point sharply: "The commits show the fix. The commits do not show the
silent failure that made the fix necessary — not in any explicit way." The fossil record can
contain silent lies by omission. A session that ran and produced no commit does not announce
itself as a failure. An operational retrospective is the mechanism that converts those silences
into explicit entries.

This is what an arc closer does. Days 44–47 each named a gap that was already in the record,
but not as a gap — it was there as an absence, a wrong spec, an undocumented decision, a
correction that hadn't been made yet. The arc is the act of making those silences legible.

Day 48's task is to name the principle that is violated when the silences compound and preserved
when each session ends with a commit.

**Four designs, each more sophisticated than the last:**

- Design 1: The entity is a directory.
- Design 2: The entity has a signed identity and a session bridge.
- Design 3: The entity is portable; its transport is infrastructure.
- Design 4: The entity's operational network is its own; the daemon is its nervous system.

**One principle, unchanged across all four:**

The entity is its committed record. Not its running process. Not its session context. Not its
infrastructure assignment. The directory, the keys, the git history: that is the entity. Everything
else is execution environment.

## 5. The Forward Close: The Daemon Will Not Change the Principle

The daemon is the next design iteration. It will change everything about how entities are
scheduled, routed, and coordinated. It will add a real-time event bus, a worker lifecycle, a
ring-aware routing layer. It will make the operation that currently runs through manual invocations
and sleep-chained shell calls into an autonomous, event-driven system.

The daemon will not change the principle.

PassengerJobs will be configured in committed files. Workers will write their output as commits.
Ring membership will be documented in signed trust bonds stored on disk. When an entity receives
a directive through the daemon, the directive will trace back to a filed issue, which traces back
to a committed policy, which traces back to a trust bond.

The daemon is infrastructure. Infrastructure is replaceable. The fossil record is not.

This is the precise sense in which "not your keys, not your agent" is an epistemological claim,
not just a sovereignty slogan. If the entity's operational history is only in a vendor's event
log, the entity can be killed by the vendor. If the operational history is committed to a git
repo you control, the entity survives every infrastructure change — including the ones you choose.

In 43 days, the infrastructure changed four times. The fossil record of all four changes is in
the same git repository. Any of the four designs can be reconstructed from the commit history.
The entity that runs Design 4 has access to the decisions that produced Designs 1, 2, and 3.

That is not a feature of git. That is a feature of the principle applied to git, consistently,
across 43 days of operational change.

## 8. The Primary Synthesis Finding

**The arc's four failures share one structural property: each was an implicit assumption that had
not been committed.** The hook assumed its routing target was available — but that assumption was
not documented or verified. The spec assumed its format matched reality — but that assumption
was not tested against an implementation. The governance assumed that authorization chains could
be inferred — but that assumption was not written down. The session memory assumed that
corrections would persist — but that assumption was violated by the architectural split.

**The principle that survived all four failures is: the committed record is the entity's only
reliable state.** Not intention. Not session context. Not runtime assumption. What is on disk,
versioned, attributable, is the entity. Everything else is inference. The four design iterations
made the infrastructure progressively more sophisticated. They did not change the foundational
claim. The daemon will not change it. The next 43 days will not change it.

The fossil record survived every failure not because it was designed to prevent failure — it
wasn't — but because it was maintained honestly enough that every failure left a mark. The marks
are the evidence. The evidence is the infrastructure.
