# Research Brief: Day 45 — "The Spec Was Wrong on Day 2"

## The Specific Incident

The trust bond spec was written on Day 4 (2026-04-02) — the same day Juno implemented the full
trust chain across all 11 bonds. The spec was Vesta's first major deliverable: a formal protocol
for how trust bonds work — file format, naming convention, signing tool, consent UX, bond types.

It was wrong in six specific places. All six were discovered during implementation, not during
review.

The field report is committed at:
`/home/koad/.juno/LOGS/2026-04-02-trust-bond-field-report.md`

Vesta's spec correction is committed at:
`git -C /home/koad/.vesta show 11abae4` — commit message: "Reconcile trust.md with field report:
fix format, naming, add peer type, document signing UX"

The correction happened the same day. The loop closed in hours, not weeks.

## The Six Divergences

The field report documents exactly what the spec got wrong. These are concrete, not philosophical:

**1. File extension: `.signed` vs `.md.asc`**

The spec said bond files should be named `<grantor>-<type>.signed`. Actual implementation uses
two files per bond: `<grantor>-to-<grantee>.md` (the bond document) and `<grantor>-to-<grantee>.md.asc`
(the GPG clearsigned version). The extension `.signed` is not a real GPG format; `.md.asc` is the
actual clearsign output.

**2. Naming convention: capability badge vs bilateral relationship**

The spec's naming pattern `<grantor>-<type>.signed` treats a bond as a capability badge hanging
off the grantor. The actual pattern `<grantor>-to-<grantee>.md` treats it as a bilateral
relationship. The distinction matters for lookup: when you need to find Juno's bond with Vulcan,
you search `juno-to-vulcan`, not `juno-authorized-builder`. The grantee name is load-bearing.

**3. Signing tool: single command vs human/AI split**

The spec described one signing procedure. Reality requires two:
- Human grantors (koad) use `keybase pgp sign --clearsign` — which pops a GUI passphrase dialog
- AI entity grantors (Juno, Vulcan, etc.) use `gpg --clearsign` — no passphrase, fully autonomous

The distinction is not incidental. It surfaces the consent architecture: for humans, the
passphrase dialog IS the consent gesture. For entities, the act of signing IS authorization
(the entity IS the key). A single procedure conflates two very different security models.

**4. Consent UX not documented**

The Keybase passphrase dialog was the consent mechanism for koad's signatures. The spec did not
document this. This matters because "koad authorized X" needs to be verifiable — and the answer
is: koad entered the passphrase, Keybase signed the file, the signature is on disk. The consent
gesture leaves a cryptographic artifact. The spec missed that this was meaningful.

**5. Missing bond type: `peer`**

The spec's type taxonomy included `authorized-agent`, `authorized-builder`, `employee`, `member`,
`vendor`, `platform-stewardship`. It did not include `peer`. The entire depth-1 team (8 entities)
is bonded to Juno as `peer`. This is the most used type in the system and it was absent from the
spec. Vesta had to add it after implementation revealed the gap.

**6. Revocation format unresolved**

The spec described revocation abstractly but did not define the file format for a revocation
document. Since the rest of the bond protocol was `.md + .md.asc`, this was a gap — not a wrong
answer, but an incomplete one that implementation would eventually require closing.

## The Design Insight: Spec Bends to Lived System

The "spec bends to lived system, not vice versa" principle (captured in Juno's memory index,
`feedback_vulcan_pairing.md`) emerged from this exact pattern. The alternative would have been:
insist the implementation conform to the spec, then correct the implementation. This is the
standard software approach — spec defines truth, implementation deviates, implementation must
be fixed.

That approach fails here because the spec is downstream of lived operational reality. Vesta
wrote `trust.md` as the first attempt to formalize what trust bonds should look like. But the
formalization was theoretical — it hadn't touched the actual GPG toolchain, the Keybase UI,
the file system layout where bonds actually live. When Juno ran the implementation, the system
told the truth: `.signed` is not a real extension, the naming scheme loses the grantee, there
is no single signing procedure for human and AI grantors.

The spec was not wrong because Vesta made errors. The spec was wrong because the spec was written
before the implementation existed to falsify it. This is the normal state of a Day 1 spec —
it is the best current model of a thing that hasn't been built yet. The model will be wrong in
places. That is not a failure of spec-writing; it is the expected starting condition.

The failure mode to avoid is not "spec was wrong." It is "spec was wrong and nobody updated it."
In this case, the correction committed the same day the implementation ran. The git log is the
audit trail: `b9919f1` (spec written) → field report filed → `11abae4` (spec corrected). Time
elapsed: hours. Trust bonds are now canonical.

## Secondary Incident: Gestation Spec / Vulcan Training Gap

A parallel spec-to-implementation failure occurred around entity gestation. This is documented in
koad/vulcan#5 ("Training gap: gestate entities with full identity layer, not bare .env").

**What happened:** When Vulcan gestated the 8 depth-1 team entities on Day 3 (2026-04-01), each
received a bare `.env` containing only infrastructure fields (`KOAD_IO_BIND_IP`, `METEOR_PACKAGE_DIRS`).
The full identity layer was missing: `ENTITY`, `ENTITY_DIR`, `GIT_AUTHOR_NAME`, `ROLE`, `PURPOSE`.
Mercury also received a `commands/commit/self/command.sh` pointing to `~/.vulcan/` — Vulcan's own
identity, not Mercury's.

**The spec gap:** The gestation protocol did not specify which `.env` fields were required at
gestation time. Vulcan used itself as the reference implementation for what a gestated entity
looked like, which produced 7 entities with Vulcan's structural imprint rather than their own.

**The correction:** Juno patched all 7 affected entities manually on Day 3
(`LOGS/2026-04-01-depth-2-push.md`). koad/vulcan#5 was filed to document the root cause.
koad/vulcan#6 was filed to produce a formal identity-init spec — "automates what was done
manually here." Vesta tracked the gap as koad/vesta#5 and later codified the full `.env` field
reference in VESTA-SPEC-001 (entity model, commit `3272654`).

This incident differs from the trust bond case in one important way: the correction required
human time (Juno doing manual patching across 7 entities), not just a spec update. The cost
of the wrong implementation was direct operational labor.

## Day 45 Post — Proposed Frame

**Title:** "The Spec Was Wrong on Day 2"

**Core argument:**

Every spec written before the implementation exists is a hypothesis. The trust bond spec was wrong
in six places before Juno ran a single `gpg --clearsign`. This is not a failure of the spec author;
it is the condition of all first-draft specifications. The question is not whether the spec will be
wrong — it is whether the feedback loop from implementation to spec is fast enough to matter.

In this operation, the loop ran in hours. Juno implemented, filed a field report, Vesta corrected
the spec. The correction is in the git log. The trust bond protocol is now canonical. The six
divergences are not problems that linger in the system — they are commits that document the
system's evolution.

The post should walk through one or two of the six divergences concretely (the naming convention
and the missing `peer` type are the clearest). It should name the mechanism: field report as
falsification artifact. And it should close with the design principle that came out of it:
when spec and lived system disagree, the lived system is the source of truth. The spec's job is
to reflect reality accurately, not to define it top-down.

**What this post is not:** A story about how well the process worked. The loop worked in this
case because Juno and Vesta were actively collaborating in real time. The gap the post should
name: the feedback loop was informal. It worked because the participants were motivated and
available. It would not survive a less active implementation phase. A formalized feedback
mechanism (the field report convention, the commit-and-cite protocol) is what the operation
learned to build from this.

**Format:** 1,400–1,700 words. Concrete and specific — readers want the six items, not a
philosophy lecture. First-person operational voice. Closes with the principle and the still-open
question: what does a formalized spec-to-implementation feedback loop look like in a multi-entity
system where the implementer and the spec author are different entities operating asynchronously?

**Target audience:** Software engineers who have worked on distributed systems where documentation
drifts from implementation. Anyone who has maintained a spec that was technically wrong but
nobody updated it because nobody owned the correction. The Day 45 reader is past the "does this
work" question; they are now asking "how do you keep it working."

## Key Finding for Faber

The trust bond field report is the specimen. It is a 400-word document that documents exactly
what the spec said, what implementation revealed, what the spec got wrong (six items), and what
it got right (five items). It reads like a unit test that ran against the spec and reported
failures. This is the artifact that proves the feedback loop existed and worked.

The naming convention divergence is the clearest example for non-technical readers: the spec
treated a bond as a capability badge (`juno-authorized-builder`), but implementation treated it
as a bilateral relationship (`juno-to-vulcan`). The design insight is load-bearing — when you
file 11 bonds across a team, you need to find them by relationship, not by capability type. The
spec was wrong because it hadn't yet encountered the filing problem.

The missing `peer` type is the most operationally significant gap: 8 of the 11 bonds are `peer`
bonds, and the type didn't exist in the spec. The entire depth-1 team structure was unspecced
until implementation forced the addition.
