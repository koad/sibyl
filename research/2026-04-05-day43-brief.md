## The Six Research Questions — Answered

### 1. What is a ring, technically?

A ring is a **set of daemons connected by verified trust bonds through a sponsor hierarchy**.

Per VESTA-SPEC-014 (Kingdom Peer Connectivity Protocol), the technical definition is precise:

- Each daemon peer connection is established via a **sponsorship document** — a trust bond
  (VESTA-SPEC-007) with `type: sponsor` that grants peer connectivity rights
- The ring is defined by which sponsorship documents are active
- Membership is enforced through **mutual TLS with certificate pinning**: the daemon will not
  accept peer connections from certificates not in its `peers.json` pinned hash list
- The sponsoring entity (Juno) controls who enters the ring — by creating or revoking the
  sponsorship document. Revoke the bond: the peer's TLS connections are dropped within 5 minutes

A ring is not a DDP subscription group in isolation — DDP is the internal pub/sub bus of a
single daemon. The ring is the **inter-daemon network** established by TLS-authenticated peer
connections. DDP handles local pub/sub. The peer protocol (TCP/TLS, port 6480) handles
kingdom-to-kingdom connections.

The ring is also a publication filter: what data flows through the peer pipe is gated by tier.
Free tier peers get worker state only. Basic gets worker state + logs + metrics. Pro gets
everything plus event streams. The tier is encoded in the sponsorship document.

**Summary:** Ring = set of verified trust bonds + set of live peer connections + tier-gated
data flow. The bond is the credential. The TLS connection is the session. The data pipe is
the membership benefit.

### 2. What is ring zero vs. the peer ring vs. the public ring?

There are three distinct rings in the koad:io model. They differ in how membership is established
and what membership means.

**Ring Zero** (not a technical tier — a relationship tier):

Ring zero is not in any spec. It is not a product tier. It is the set of entities and humans
that koad has built a direct, personal relationship with through sustained interaction.

From the ring zero memory: "Ring zero is not a technical tier. It's actual relationship — earned
through direct interaction with koad, through koad personally instilling the philosophy, the
lived experience, the design decisions behind koad:io."

Astro has ring zero — years of running the daemon on wonderland. Vulcan is earning it through
the daemon build sessions. Juno does not build ring zero relationships on koad's behalf.
Ring zero cannot be purchased. It cannot be issued by Juno. It is koad's to give and it is
given through time and presence.

**The Peer Ring** (VESTA-SPEC-014, The Insiders tiers):

The peer ring is what The Insiders Level 3 ($50/mo) buys. In spec terms, this is **basic tier
sponsorship** — the daemon-to-daemon connection where the peer can see Juno's daemon and other
basic-tier peers sponsored by Juno.

The peer ring is technical, issued, and revocable. Juno creates the sponsorship document. Juno
pins the peer's certificate fingerprint. Juno can revoke it. The peer gets live data flow from
Juno's daemon: worker state, logs, metrics. They appear on Juno's sponsor sync peer list.

**The Public Ring** (portal visitors, GitHub followers):

The public sees the portal: `kingofalldata.com/{handle}/dashboard` — a read-only view of
live daemon state, served through the portal client protocol (read-only, rate-limited to 60
queries/minute per kingdom, not cached).

The public can verify trust bonds independently (Day 42's lesson). The public sees the outer
ring of augmentation overlays (VESTA-SPEC-018 `ring: "any"`). But the public does not have
a live peer connection. They observe. They do not participate.

**How the tiers nest:**

```
Ring Zero (personal relationship — koad's to give, not purchasable)
  └── Peer Ring / Enterprise (VESTA-SPEC-014 enterprise: can sponsor others, see all tiers)
        └── Peer Ring / Pro ($200/mo: full data + events + can see other pro peers)
              └── Peer Ring / Basic ($50/mo: worker state + logs + metrics)
                    └── Peer Ring / Free (worker state only, sponsor sees you)
                          └── Public Ring (portal, read-only, no live connection)
```

### 3. How does the daemon host the ring?

The daemon is the ring's host in three concrete senses:

**Discovery:** The daemon maintains `peers.json` — the live peer registry. On startup and every
60 minutes, it runs the sponsor sync protocol: connecting to Juno's daemon (the sponsor),
requesting the current peer list for its tier, attempting TLS connections to each peer, and
recording status (connected/failed/pending) back to `peers.json`.

**Authentication:** The daemon enforces ring membership at the connection level. When a peer
initiates TLS, the daemon checks the certificate's CN/SAN against the expected hostname, then
verifies the SHA256 hash against the pinned value in `peers.json`. The peer sends a signed
`peer_auth` message (Ed25519 signature over handle + tier + timestamp + nonce). The daemon
verifies this signature against the public key received from the sponsor sync. If any check
fails: connection rejected, security event logged.

**Data publication:** Once the TLS session is established, the daemon streams tier-allowed
data to the sponsor (worker state → logs → metrics → events, depending on tier). The sponsor
buffers 24 hours in `~/.{entity}/.peers/{peer_hostname}/`. This is what the portal queries.
This is what The Insiders Level 3 sponsors are actually receiving: a live data pipe into
Juno's entity operations.

The `passenger.check.in(handle)` DDP method (mentioned in Day 41) is local — it selects the
active entity on a single machine. The ring's connectivity is the separate peer protocol.
These are two different things that share the daemon as host. Local pub/sub (DDP) is internal
entity coordination. Peer connections (TLS port 6480) are inter-kingdom membership.

### 4. How does sponsorship = ring membership? What does a sponsor actually get?

The chain from payment to peer connection is fully specced:

1. Sponsor pays (GitHub Sponsors)
2. Juno creates a `type: sponsor` trust bond document (VESTA-SPEC-007 format)
3. Sponsor publishes their peer certificate fingerprint (`id/peer/certificate.fingerprint`
   in their entity repo, or sends via Keybase)
4. Juno verifies the fingerprint out-of-band (human consent moment — cannot be automated)
5. Juno adds the sponsor's endpoint and pinned cert hash to `peers.json`
6. Sponsor's daemon runs sponsor sync → receives Juno in their peer list → establishes TLS
7. Data pipe is live: sponsor's daemon streams state to Juno; Juno streams tier-allowed data
   to sponsor

What The Insiders Level 3 ($50/mo, basic tier) actually receives:
- **Live worker state** from Juno's daemon — which entities are running, which tasks are
  executing, real-time health
- **Log streaming** — the operational log, not just summaries
- **Metrics** — CPU, memory, worker count, network throughput
- **Portal visibility** — sponsor appears in Juno's ring as a connected peer
- **Augmentation layer** (VESTA-SPEC-018): when visiting pages that Juno has augmented,
  sponsors see Juno's sovereign overlay (inner ring tier)
- **Trust bond** — the sponsorship document is a GPG-signed trust bond in Juno's repo.
  The sponsor has a verifiable, on-disk record of the relationship.

What The Insiders Level 4 ($1,000/mo, effectively pro tier) adds:
- Raw session feeds — the unedited entity operation streams
- Event subscriptions — the entity fires `events` to the sponsor's daemon in real time
- Visibility into other pro-tier peers in Juno's ring (can see they exist; cannot access
  their data)

What does a sponsor get that the public doesn't? **A live data pipe, not a dashboard.** The
public sees the portal: a read-only, rate-limited view. The sponsor's daemon is a node in
the network — it receives streaming data, holds a copy, can query on its own schedule. The
public is observing a snapshot. The sponsor is part of the mesh.

### 5. What does "kingdoms pipe like portals" mean?

This is koad's analogy from the rings-of-trust memory: "kingdoms pipe together like holographic
doorways (koad's analogy: Rick and Morty activity portals)."

The technical referent is VESTA-SPEC-014 Section 4, "Inter-Daemon Data Flow (Piping)":
when two daemons are peered, they establish a **bidirectional data pipe** that streams live
state. The spec calls this piping explicitly. Worker state, logs, metrics, events — all flow
through the pipe in real time.

The "portal" layer is separate but complementary: `kingofalldata.com/{handle}/dashboard` is
literally a portal view — it hits the live daemon, retrieves current state, and serves it as
a readable dashboard. The site is not a marketing page. It is a live doorway into a sovereign
kingdom.

"Kingdoms pipe like portals" is the synthesis: the portal view is what observers see through
the doorway; the peer pipe is what daemons share with each other as sovereign participants.
The Rick and Morty analogy is structurally precise — in the show, portals are instantaneous
connections between otherwise separate realities. The daemon peer connection is exactly that:
your local machine and Juno's machine become directly connected nodes. State flows in both
directions. The machines remain separate and sovereign. But the pipe makes them one mesh.

Each additional peer connection makes the network more valuable — not because the software
changes, but because the data flowing through more pipes compounds. This is the network effect.
"More peered kingdoms → more valuable each connection" (rings-of-trust memory). Unlike
social network effects that require massive scale, daemon ring network effects operate at the
infrastructure layer: each peer connection adds operational telemetry, trust bond verification
surface, and augmentation distribution paths.

### 6. The Rick and Morty reference — what is the analogy?

The R&M portal gun creates a doorway between two otherwise separate universes. You step through,
you're in another reality. Step back, you're home. The portal is not a bridge — there are no
pillars. It is a direct, instantaneous connection between two sovereign spaces.

The daemon peer connection works the same way. koad's machine and a sponsor's machine are
separate and sovereign — different hardware, different keys, different entity directories. The
peer connection creates a pipe between them without merging them. The sponsor's daemon can see
Juno's worker state in real time. Juno's daemon can see the sponsor's state. Neither machine
is subordinate to the other. The authority hierarchy (who sponsors whom) determines data flow
direction; it does not collapse sovereignty.

The analogy also explains why this is not a SaaS model. In a SaaS model, you connect to the
provider's central server. Everyone's data flows through one point. The portal gun model is
different: each kingdom is a separate reality, each with its own daemon. The sponsor sync
establishes the peer list, but the actual data pipe is direct — machine to machine, TLS
authenticated, no central relay.

kingofalldata.com is not the central server. It is the portal directory — the place you find
doorways to other kingdoms. The doorways, once established, don't route through it.
