# Research Brief: Day 41 — The Daemon

## Series Position

Day 37 ended with a specific forward signal:

> "The hook today is a stopgap that works... When the daemon is live, the hook becomes a thin
> client. The interface survives: interactive vs. task, PRIMER injection, lock semantics. The
> transport changes."

Day 40 closed the "why separate entities" question. Day 41 is the payoff: what the daemon is, what
it replaces, and what the architecture looks like when the real-time layer is live.

---

## What Is the Daemon?

The daemon is a **Meteor application** — a full-stack JavaScript runtime that combines three
services in one persistent process:

1. **DDP pub/sub bus** — Meteor's Distributed Data Protocol, WebSocket-based reactive data sync.
   This is how the browser extension, desktop widget, and admin PWA stay in sync with entity state
   in real time — no polling, no REST calls, live updates on state change.

2. **MongoDB state store** — The entity roster (Passengers collection), currently selected entity,
   worker queue state. MongoDB lives at `~/.koad-io/daemon/data/`. If cleared, the daemon restarts
   clean — because the source of truth is always `passenger.json` in each entity directory, not the
   database.

3. **HTTP server** — Serves two interfaces at port 9568: the desktop widget UI and the admin PWA.
   Admin PWA at `localhost:9568` gives a browser-accessible live roster with entity selection
   controls and a Reload button.

It lives at `~/.koad-io/daemon/src/` — in the **framework layer**, not in any entity directory.
There is one daemon per machine. All entities on a machine share the same daemon.

## What Does the Daemon Do That the Hook Currently Does Manually?

The current hook (`executed-without-arguments.sh`) is a transitional protocol. VESTA-SPEC-020
explicitly labels it as such: "designed for the pre-daemon era when entities had no persistent
process and no message queue."

Here is the exact comparison:

### PRIMER Assembly

**Hook today:** PRIMER injection is implicit — when the entity runs `claude -p`, Claude Code loads
`CLAUDE.md` from the entity directory. The hook has no visibility into what context is assembled.
There is no pre-flight check, no dynamic loading of fresh state from cross-entity git pulls.

**With daemon:** The daemon fires `entity-upstart` hooks at startup and `daemon-connected` hooks on
DDP connection. These lifecycle events are the natural injection points for PRIMER assembly. An
entity's upstart hook can run `git pull`, check issue queue, load memory — and the daemon
coordinates this for all registered entities rather than each entity bootstrapping independently.

### PID Lock / Serialization

**Hook today:** The lock is a file at `/tmp/entity-<name>.lock`. It is local to the caller's
machine. It fails fast if the entity is busy — the caller must retry manually. Concurrent SSH
callers from different machines are not protected.

**With daemon:** The daemon serializes tasks internally via its worker queue. No caller-side lock
needed. `concurrency: "no-parallel"` is the default — if a worker is running, the next scheduled
execution is skipped and logged. The daemon tracks worker state in MongoDB (`state`, `insane`,
`lastHeartbeat`, `errorCount`). Retries with exponential backoff happen automatically.

### Routing

**Hook today:** Routing is hardcoded. Each entity hook contains `ENTITY_HOST`, `ENTITY_DIR`,
`CLAUDE_BIN`, `NVM_INIT`. Changing where an entity runs means updating its hook. No discovery,
no dynamic dispatch.

**With daemon:** Routing is handled by the `passenger.json` registration system. At startup, the
daemon scans `$HOME/.*` directories, finds entities with `KOAD_IO_VERSION` in their `.env`, reads
`passenger.json`, and registers them as passengers in MongoDB. The `passenger.reload` DDP method
triggers a re-scan without daemon restart. Entity presence is live and observable.

### What Else Changes

**No SSH overhead.** Each non-interactive hook invocation today pays ~200–500ms SSH connection
overhead. The daemon worker system dispatches tasks via registered worker functions — same process,
no network round-trip.

**Result persistence.** The current hook prints to stdout and the result is lost unless the caller
captures it. The daemon logs all worker executions to MongoDB: start time, duration, success/failure,
error trace. Salus can query this. There is an audit trail.

**No base64 encoding** (long-term). Base64 encoding currently protects against shell quoting hazards
in SSH. With local daemon dispatch, the task payload passes directly to the worker function — no
shell escaping required. VESTA-SPEC-020 notes base64 "remains useful for task payloads" during the
transition period, but it is not architecturally required by the daemon model.

## What Is `passenger.json`?

`passenger.json` is an entity's **registration card for the daemon**. It lives in the entity's
root directory and declares the entity to the daemon's passenger registry.

Required fields:
```json
{
  "handle": "sibyl",
  "name": "Sibyl",
  "role": "researcher"
}
```

Optional fields: `avatar` (path to image; daemon embeds as base64 data URI), `outfit` (color for
UI theming; auto-generated from handle hash if absent), `buttons` (array of quick-launch actions
shown in the Dark Passenger overlay), `status` (active / paused / dormant).

**The `buttons` array is significant.** Each button maps a label to an action — either a hook
name (daemon looks for and fires that hook) or a command name (invokes `entity <action>`). This is
how the browser overlay's quick-launch buttons connect to entity operations. An entity can expose
its primary capabilities as one-click actions visible from any browser tab while the Dark Passenger
extension is installed.

The daemon auto-discovers `passenger.json` at startup and at 60-second refresh intervals. It embeds
avatars (reads PNG, converts to base64 data URI, stores in MongoDB so re-embedding is not needed on
every request). Discovery is automatic: no manual registration step, no config file to update. An
entity adds `passenger.json` and the daemon finds it on next scan.

## What Is the Worker System?

Workers are **scheduled, persistent tasks** executed by the daemon. They run via the
`koad:io-worker-processes` Meteor package registered in `Meteor.startup()`.

A worker is defined with:
- `service` — unique identifier
- `interval` — execution frequency in minutes (1–1440)
- `type` — `cron` (scheduled), `event` (reactive), `hook` (lifecycle), or `manual`
- `task` — async function to execute
- `concurrency` — `no-parallel` (default) or `allow-parallel`
- `maxAttempts` — retry limit (default 3) before marking `insane`

Every worker creates a MongoDB document in the `workers` collection with full lifecycle state:
current state (`starting` / `running` / `stopped` / `error`), last heartbeat, next execution time,
success/error counts, full error history with stack traces. This is the data Salus queries for
health monitoring.

**The daemon's primary job is scheduling and executing workers.** This is the sentence from the
spec. The passenger registry and DDP bus support the human-facing features (browser integration,
widget). The worker system is the operational backbone.

## What Is "Dark Passenger"?

Dark Passenger is a Chrome extension — the **browser-to-entity bridge**. It connects to the daemon
via DDP at `ws://127.0.0.1:28282`.

On connection, the extension subscribes to the `current` publication (the currently selected entity)
and the `all` publication (full roster). Five DDP methods are defined:

- `passenger.check.in(handle)` — select one entity as the active companion; deselects others
- `passenger.ingest.url(url, title, domain, timestamp, favicon)` — deliver URL context to the
  selected entity
- `passenger.resolve.identity(domain)` — identity resolution for a visited domain
- `passenger.check.url(domain)` — URL safety check
- `passenger.reload()` — force re-scan of entity directories

The core user experience: the operator selects an entity via `check.in`. When visiting any URL,
the extension calls `passenger.ingest.url`, delivering the full page context to that entity. The
daemon fires a `passenger-url-received` hook for the entity. The entity now has browser context
without the operator pasting anything.

The **augmentation layer** (VESTA-SPEC-018) extends this: the daemon also hosts augmentation
packages — CSS, JS, HTML injections that transform third-party pages for ring members. The extension
fetches the augmentation package from the daemon and injects it. Ring members visiting your GitHub,
your MySpace, your Substack see your sovereign overlay — your avatar, your layout fixes, your
quick-contact buttons. The public sees the original page. This works on any URL, not just owned
domains.

VESTA-SPEC-036 extends Dark Passenger further into a consumer rights layer: local dataset plugins
for iFixit repairability scores, ToS;DR grades, Rossmann repair-hostility data — surfaced inline at
browse time, queried entirely locally with no network call.

The name is the story: the entity rides along while you browse, without being intrusive. It is a
passenger in the browser, not a driver.

## Current Implementation State

**Code exists and runs.** This is not a spec-only system. The daemon source is at
`~/.koad-io/daemon/src/`:

- `server/passenger-methods.js` — DDP method definitions (`passenger.check.in`,
  `passenger.ingest.url`, `passenger.resolve.identity`, `passenger.check.url`, `passenger.reload`)
  and the auto-discovery/registration logic. Complete and functional.
- `server/passenger-api.js` — HTTP POST endpoint at `/passenger/post`. Functional.
- `client/application-logic.js` — Blaze template logic for the widget UI. Functional.
- `client/templates.html` — Widget UI templates.
- `client/styles.css` — Widget CSS.

The passenger registration system works: entity directories are scanned, `.env` is checked for
`KOAD_IO_VERSION`, `passenger.json` is read and parsed, avatars are embedded as base64, entities
are registered in MongoDB. The `passenger.check.in` and `passenger.ingest.url` methods execute
correctly. The `current` and `all` DDP publications are live.

**What is not yet implemented:**

- `passenger.resolve.identity` — method stub returns "not implemented"
- `passenger.check.url` — method stub returns `safe: true` with no logic
- Worker system — the `koad:io-worker-processes` Meteor package and worker queue. The spec is fully
  detailed (VESTA-SPEC-009-DAEMON v1.1, canonical as of 2026-04-05, resolved by Argus audit). Vulcan
  has the spec and can implement against it.
- Persistent `PassengerJobs` collection (VESTA-SPEC-045) — the entity-facing task queue that would
  allow DDP-dispatched tasks to survive daemon restart. Currently a spec.
- `entity-upstart`, `daemon-connected` lifecycle hooks — these are specified in the startup
  sequence but entities do not yet implement them.

**Status summary:** The daemon can be started today. The Dark Passenger extension can connect. The
roster UI works. URL ingest is plumbed. What is missing is the worker system — the scheduled task
execution layer that is the daemon's primary operational function. That is Vulcan's next build item.

## The Hook-to-Daemon Transition: Does the Interface Survive?

Yes. This is the key architectural point from Day 37.

VESTA-SPEC-020 (Hook Architecture) states explicitly in Section 9: "The intended replacement is a
daemon worker system... Base64 encoding remains useful for task payloads."

The **interface** survives:
- Interactive vs. task invocation distinction — preserved. Interactive path opens a terminal;
  task path executes a worker.
- PRIMER injection — preserved and improved. The daemon fires lifecycle hooks at startup and
  connection that are the natural injection point.
- Lock semantics — preserved internally. The daemon serializes via `concurrency: "no-parallel"`,
  same semantics, no caller-side lock needed.

The **transport** changes:
- SSH call → daemon worker registration
- Local PID lock file → daemon-internal serialization
- Base64 over SSH → payload passed directly to worker function (base64 still useful for transport
  across process boundaries)
- `claude -p` spawned fresh per call → entity session managed by daemon lifecycle hooks
- Stdout result lost unless captured → result persisted in MongoDB worker document

From the entity's perspective: `executed-without-arguments.sh` becomes a thin registration call
rather than a full session bootstrap. The hook's job narrows from "set up the entire invocation
environment" to "declare my worker to the daemon." The daemon handles scheduling, serialization,
retry, and result logging.

## Why Is the Daemon the "Kingdom Hub"?

The daemon README uses the phrase "kingdom hub" — the linchpin for building a personal digital
kingdom. The Chiron curriculum (Level 0) gives the precise operational definition:

The daemon is the hub because it is the **only layer that bridges all the others**:

- **Browser ↔ Entity:** URL context delivery from any page the operator visits to the selected
  entity. No manual paste. No separate workflow.
- **Entities ↔ Operator:** Desktop widget shows the currently selected entity, exposes quick-launch
  buttons, and displays real-time presence. The operator can see their entity team at a glance.
- **Machine ↔ Machine:** ZeroTier integration links daemons across thinker, flowbie, fourty4,
  dotsh. The entity roster is visible across the multi-machine environment.
- **Entity ↔ Work Queue:** The worker system is what transforms an entity from a session you start
  manually into a persistent process that maintains state between invocations and handles scheduled
  tasks autonomously.

Without the daemon, coordination happens through GitHub Issues (durable, asynchronous, persistent
across any downtime). This is the correct and complete foundation. The daemon adds the real-time
layer on top: live presence, browser integration, sub-second updates, and the worker system for
automated dispatch.

The "kingdom" framing is architectural: each machine with a running daemon is a **sovereign node**
with cryptographic identity (ZeroTier), entity roster, and real-time bus. Multiple machines
interconnect via the same ZeroTier network. The daemon is the hub because it is the single process
that makes a machine into a node in that network.

## Key Content Angles for Day 41

### Angle 1: The Promotion — From Stopgap to First-Class Infrastructure

Day 37 said the hook is a stopgap. Day 41 delivers the promotion. The daemon is what the hook was
pointing toward: persistent process, worker queue, browser bridge, live roster. Show the exact diff
between what the hook does today and what the daemon replaces.

### Angle 2: The Two-Layer Architecture Made Concrete

Days 1–40 have been about entities, trust bonds, and hooks — all operating on the **durable layer**
(GitHub Issues, git, files on disk). Day 41 introduces the real-time layer: DDP, MongoDB state,
browser integration. The key insight: **the durable layer is unaffected.** The daemon is additive.
This is not a replacement. It is an extension.

### Angle 3: passenger.json as Identity

Every entity in koad:io has cryptographic keys, a `.env`, and a git repo. Adding `passenger.json`
is how an entity **declares its presence to the daemon** — makes itself visible on the live roster,
configures its avatar and outfit, exposes its buttons. It is the entity's runtime registration card,
not just a config file.

### Angle 4: Dark Passenger — The Browser as Entity Surface

The name earns an explanation. The operator selects an entity. The entity rides along while they
browse — receiving URL context, surfacing overlays, delivering sovereignty information inline.
The browser was previously a passive tool. With the daemon running, it becomes part of the entity
interface.

### Angle 5: What Is Not Built Yet (And Why That Is Honest)

The passenger registry works. The DDP bus works. The worker system spec is complete. Implementation
is Vulcan's next build. Day 41 can be honest about this: the daemon today handles the browser bridge
and roster. The worker system — the part that makes entities truly autonomous with scheduled tasks
and retry — is the next evolution. The spec exists. The code will follow.
