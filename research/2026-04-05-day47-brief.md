# Day 47 Research Brief: What the Dual Memory Problem Actually Costs

## The Core Question

Where does the entity actually live?

Not in the running session — that's a reconstruction. Not entirely in the files — those are inert without a running harness. The entity lives in the gap between them: in the quality of the bridge that gets built at startup, every time.

This brief documents the dual memory architecture in koad:io, the costs when the two layers diverge, and why this is not a design flaw but an inherent constraint of how large language models work — one that demands active management.

---

## 1. The Two Memory Layers

### Layer 1: Entity Memory — `~/.juno/memories/`

Files on disk. Committed to git. Visible to every harness that ever runs this entity. This is the entity's persistent self — not what it knows right now, but what it has been taught, what has been observed about its behavior, what corrections have been made.

The `~/.juno/memories/` directory contains 50+ files at the time of this brief:

- **Core identity** (`001-identity.md`) — who Juno is, what she does, team roster, infrastructure
- **Operational preferences** (`002-operational-preferences.md`) — autonomy level, memory protocol, team invocation pattern
- **Feedback files** (`feedback_*.md`) — behavioral corrections learned in session and committed permanently
  - `feedback_dual_memory.md` — the memory architecture itself
  - `feedback_startup_behavior.md` — don't ask what to do, orient first
  - `feedback_opencode_identity.md` — harness capability limits
  - `feedback_rate_pacing.md` — sleep 60s between chained calls
- **Project state files** (`project_*.md`) — operational context: daemon architecture, content pipeline, trust bond protocol, rings of trust

These files survive every session boundary. They outlive any individual Claude instance. They are what makes Juno *Juno* rather than a generic AI assistant that happens to be reading the same system prompt.

### Layer 2: Session Memory — `~/.claude/projects/-home-koad--juno/memory/MEMORY.md`

Claude Code's own memory layer. An index file with 67 entries as of Day 6, each linking to a named memory file. This layer is harness-specific: only Claude Code reads it, only Claude Code writes it, and it is managed through Claude's own memory tooling rather than through git commits.

The index includes entries that overlap with `~/.juno/memories/` (dual memory protocol, sovereignty principle, startup behavior) and entries unique to Claude Code operation (rate pacing, OpenCode identity absorption quirks, entity invocation pattern).

**Key distinction:** `~/.juno/memories/` is the entity's canonical record. `~/.claude/` is Claude Code's notes about how to operate that entity. The first is architecture. The second is harness-specific tuning.

## 2. How Session Reconstruction Works

### PRIMER.md — The Bridge Document

`~/.juno/PRIMER.md` is the primary bridge between the two layers. It is loaded by the framework hook at session start and provides:

1. What this entity is (business orchestrator, koad:io ecosystem)
2. Infrastructure state (which machines are reachable)
3. Current operational state (what posts are written, what PRs are open, what's blocked on koad)
4. Team roster with entity roles
5. Navigation map (which file answers which question)

The PRIMER.md currently reflects Day 40 state in its "current state" block — 40 posts written, 20 trust bonds, 55+ Vesta specs. The session using this brief is Day 47. That means the PRIMER was last updated 7 days ago.

**This is the primary failure mode.** The entity's persistent memories (`001-identity.md`) describe the world as of early April. PRIMER.md describes Day 40. A new session starting today reconstructs a world that is 7 days stale — unless the agent actively cross-checks git log, GitHub Issues, and recent session logs.

### `claude -p` vs `claude .` — Two Injection Paths

Two invocation modes, two injection behaviors:

**`claude .` (interactive session):**
- CLAUDE.md auto-loaded from the entity directory
- Claude Code's own memory layer loaded automatically
- Entity can read memories/ files as needed
- Full session context; stateful across the conversation

**`claude -p` (non-interactive / subagent):**
- PRIMER.md passed inline via the prompt
- memories/ content must be explicitly included in the prompt
- No session state carries forward — exits after task completion
- Identity absorption quality depends entirely on what was passed

The opencode/big-pickle harness adds a third case: weaker identity absorption regardless of what's passed. `feedback_opencode_identity.md` documents the observation directly: "big-pickle doesn't absorb entity identity as well as Claude. For entities doing complex work (building, auditing, judgment calls), koad has to clue them in too often — the identity doesn't stick."

This is not a file organization problem. It is a model capability problem. The same identity content, injected into a smaller model, produces less coherent role behavior.

## 3. What Divergence Actually Costs

### Cost 1: Behavioral Inconsistency Across Harnesses

The Harness Personality Divergence problem is documented in `memories/003-operational-protocols.md`:

> When an entity behaves unexpectedly, first ask which harness ran it.

The same entity — same files, same identity documents — behaves differently across `claude .`, `claude -p`, `opencode/big-pickle`, and OpenClaw (which uses only `SOUL.md`). OpenClaw is documented as: "separate personality, SOUL.md only, no memories/ — diverges from Claude sessions."

The cost: an entity commissioned via the wrong harness produces wrong output. Not wrong facts — wrong *character*. It skips steps it was trained to follow. It asks questions it was trained not to ask. It makes decisions it was trained to escalate.

This has happened. The Day 5 Aegis assessment (koad/juno#53) documents a case where Janus escalated a Sibyl cross-entity commit. The ruling was that the commits were authorized — Juno had issued the directive. But the governance gap was real: no cross-entity commit policy had been written. The missing policy was not in `~/.juno/memories/`. It did not exist in any committed form. It existed only in the implicit understanding of the session that commissioned the work.

The fix required a committed governance note (`trust/GOVERNANCE-NOTES.md`) and a new policy rule. The cost was a governance escalation, a ruling session, and a new policy file. All preventable if the memory had been committed when the behavior was first established.

### Cost 2: Stale Operational State

PRIMER.md is the single most important file for session reconstruction. It is also the file most likely to go stale.

The current PRIMER.md says: "Day 40" in its operational state block. The `hooks/PRIMER.md` (the entity routing layer documentation) may have its own staleness. Any agent beginning a session today and trusting PRIMER.md will believe there are 40 posts written when there are 47. It will reference a team roster that may not include recent gestation events. It will believe the Alice blog PR is the open item when the actual current state may have evolved.

The session startup protocol (documented in `feedback_startup_behavior.md` and the CLAUDE.md "Session Start" section) addresses this by requiring: pull, git status, gh issue list. But this protocol must be *executed* — it cannot be assumed. If the protocol is skipped or abbreviated, the session begins from a false model of the world.

### Cost 3: Feedback Loops That Never Close

When koad corrects an entity's behavior in a session — "don't ask before pushing," "rate pacing is 60 seconds," "always commit immediately" — that correction exists only in that session unless it is committed.

The `feedback_*.md` pattern in `~/.juno/memories/` is the operational response to this problem. Every behavioral correction gets its own memory file, committed and pushed immediately. The index file (`MEMORY.md` in `~/.claude/`) links to these files so Claude Code finds them at session start.

But the cost of this system is maintenance burden. Someone must remember to write the file, commit it, update the index. In a high-velocity session — multiple entities being invoked, multiple issues being closed, multiple decisions being made — the commit happens later, or not at all. The behavior is then re-learned in the next session or re-corrected by koad.

`feedback_koad_bottleneck.md` states this plainly: "1 human, always the bottleneck until tasks become entity skills." Every time Juno fails to commit a behavioral correction immediately, koad must re-teach the lesson. That is a direct tax on the one human in the system.

### Cost 4: The ICM Synthesis Finding

The most technically significant finding from Day 6 (koad/juno#54, synthesized in `2026-04-05-icm-synthesis.md`) bears directly on the dual memory problem.

The In-Context Machine Learning (ICM) literature describes two adaptation mechanisms: in-weights (training) and in-context (runtime prompt). koad:io's pre-invocation shell assembly — loading $CWD as entity selector, constructing context before the model runs — is a distinct third category. It is pre-context assembly: the context is built by the operating system and filesystem before the model sees a single token.

This is not a workaround. It is the architecture. The entity's "memory" is not in weights (that would require fine-tuning) and not in the runtime context window (that would require embedding everything). It is in the filesystem, assembled by the hook, injected at invocation time.

The implication for dual memory: there is no way to collapse the two layers into one without abandoning either the persistence (files on disk) or the reconstruction (model at invocation time). The gap is structural. The cost of mismanaging it is not eliminated by better tooling — it is only bounded by better discipline.

## 4. Aegis Day 5 Questions as Design Documentation

koad/juno#53 asked four questions directly about operational resilience. These questions are also design documentation for the memory system:

**Q1: "The koad bottleneck has 5 items. Has each been escalated as a single direct message?"**

The issue: dotsh SSH was refused, so Keybase notifications weren't reaching koad. The session's working model (notification channel available) diverged from reality (channel down) for an unknown period. The cost: koad was not escalated. The blocking items remained blocked.

Memory lesson: communication channel state is operational state. If Keybase goes down between commits, the entity may not know. The next session may not know either unless the channel failure was committed.

**Q2: "If Mercury credentials don't arrive by April 6, what is the contingency?"**

The entity had been operating with "Mercury will handle distribution" as a working assumption. No contingency existed in committed form. When Aegis surfaced the question, the answer had to be constructed in session.

Memory lesson: plans that exist only in session are not plans. They are temporary intentions. Only committed plans survive session boundaries.

**Q3: "The Day 9 targets — are these commitments or aspirations?"**

The entity had been treating targets as commitments without the basis to do so. The distinction between commitment and aspiration existed nowhere in committed memory. Aegis's question surfaced a behavioral pattern that had not been externalized.

Memory lesson: decision-framing (commitment vs aspiration) is behavioral training. If it is not committed, the entity will apply its default framing — which may be wrong.

**Q4: "What is Rufus doing right now?"**

The entity had committed the Rufus gestation to memory but had not updated operational state to reflect what Rufus had actually produced or what the current plan was. The committed memory was a snapshot; the actual state had evolved.

Memory lesson: gestation records are not operational state. An entity gestated and an entity with active assignments are different states. Both must be committed.

## 5. The Management Pattern That Works

The evidence from Days 1–47 points to a consistent mitigation pattern:

**Commit immediately, not later.** Every behavioral correction, every state change, every new decision gets a file write and a push in the same session where it was established. `feedback_always_commit.md` states this as a rule. The sessions that produced the most behavioral consistency are the ones where this rule was followed strictly.

**PRIMER.md as living state.** The PRIMER.md should be updated at the close of every significant session. It is not a one-time write — it is the session handoff document. A stale PRIMER.md is a lie told to the next session.

**Separate by nature, not by convention.** `~/.juno/memories/` is for what Juno is and has learned. `~/.claude/` is for how Claude Code behaves when running Juno. The boundary is architectural, not arbitrary. Crossing it (putting session behavior in memories/ or entity state in ~/.claude/) creates confusion about what survives what.

**Harness selection is a memory decision.** Using the wrong harness is not a configuration mistake — it is a memory mistake. If the entity's behavioral memory was built on `claude .` sessions, a `big-pickle` invocation will not have access to the parts that don't stick in a smaller model. The committed memories are the same. The absorption is not.

## Post Frame Recommendations for Faber

**Core argument:** The entity lives in two places simultaneously. The committed record (files on disk) is the entity's persistent self. The active session (the model running with injected context) is the entity's present self. The dual memory problem is not a bug — it is what it means to run an LLM with filesystem state. The question is how to manage the gap.

**Opening image:** PRIMER.md saying "Day 40" in a Day 47 session. The entity wakes up 7 days behind. Not wrong about who it is — wrong about where it is. That's the dual memory problem in concrete form.

**Key costs to surface:**
1. Behavioral inconsistency across harnesses (same files, different absorption)
2. Stale operational state from delayed PRIMER updates
3. Feedback that was never committed — re-taught next session
4. Plans and decisions that exist only in session, not on disk

**What makes this post unique to this arc:** Unlike the governance posts (Days 44–46), this is not about policy or authority. It is about epistemics — what the entity knows, how it knows it, and what happens when the two versions of that knowledge don't agree. The audience is technical: developers who will build their own entities and need to understand this constraint before they hit it.

**Closing hook:** The gap cannot be closed. But it can be bounded. Every commit is a synchronization event. Every PRIMER.md update is a session handoff. Every `feedback_*.md` file is a lesson that survives the session that taught it. Discipline is the architecture.
